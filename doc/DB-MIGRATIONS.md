# DB 마이그레이션

## 지원 기준

`src/main/migrations/legacy-schema.json`은 2026-10-07 리팩토링 전 17개 테이블의 DDL·컬럼·외래 키를 고정한 기준이다. 기존 개발 DB와 일치함을 확인했다. 이 파일과 이미 배포한 마이그레이션은 변경하지 않는다.

- 빈 DB: Baseline이 기준 테이블을 생성한 뒤 후속 마이그레이션을 실행한다.
- 이력 없는 기존 DB: 기준 스키마와 필수 인덱스를 검증하고 이력만 도입한다. 알 수 없는 구조는 자동 보정하지 않고 시작을 중단한다.
- 이력 있는 DB: 미적용 마이그레이션만 실행한다. 현재 앱이 알 수 없는 이력이 있으면 구버전 앱의 실행을 중단한다.
- 현재 `CB_STOCK_BUY.QUANTITY`, `CC_TRADE.QUANTITY`는 **INTEGER**다. 소수 주식 수량은 지원하지 않는다.
- `FractionalQuantity1791370000001`은 앞선 리팩토링 중 적용된 REAL 변경 이력이다. 실제 개발 DB에 적용된 것을 확인했으므로 이미 적용된 마이그레이션은 삭제·변경하지 않는다.
- `IntegerQuantity1791370000002`가 정수 수량 정책을 복원한다. 두 테이블의 원시 값을 먼저 검사하고 모두 정수인 경우에만 INTEGER로 변경한다. 행·외래 키·인덱스·사용자 트리거·AUTOINCREMENT 최댓값을 보존한다. 소수 또는 숫자가 아닌 값이 있으면 반올림·절삭 없이 시작을 중단한다.
- 신규 DB도 고정된 이력을 순서대로 실행하며 최종 수량 타입은 INTEGER다. 기존 INTEGER DB 및 REAL 변경이 적용된 DB 모두 같은 최종 스키마와 3개 이력을 갖는다.

## 시작 및 복구

1. `synchronize: false`, `migrationsRun: false` 상태에서 DB를 연다.
2. 기존 파일에 적용할 변경이 있으면 SQLite `VACUUM INTO`로 WAL을 포함한 일관된 백업을 만든다. 경로는 원본 옆의 `.before-migration-날짜-UUID.bak`이다.
3. 미적용 변경 전체를 하나의 트랜잭션으로 실행한다. 정수 수량 전환 후 외래 키 무결성도 검사한다.
4. 성공한 뒤에만 초기 데이터와 창을 생성한다. 실패하면 롤백·연결 종료 후 오류와 백업 경로를 안내한다.
5. 복구 시 앱의 모든 창과 프로세스를 종료한다. 실패한 DB 및 남아 있는 `-wal`, `-shm` 파일은 조사용으로 다른 위치에 보관하고, 안내된 백업을 원래 DB 파일명으로 복사한다. 수정된 앱으로 다시 실행한다. 실행 중인 DB 파일을 덮어쓰지 않는다.

역방향 마이그레이션은 제공하지 않는다. 이전 버전으로 복구해야 할 때는 업그레이드 전 백업을 사용한다. 정수 수량 복원은 데이터 검사와 백업을 갖춘 별도의 순방향 마이그레이션으로만 제공한다. 백업 이후 기록한 데이터는 해당 백업에 없으므로 별도 보존해야 한다.

## 변경과 검증

새 타임스탬프와 명시적인 `name`을 가진 MigrationInterface를 작성하고 `createDataSource.ts` 배열 끝에 등록한다. 정적 import로 webpack 번들에 포함한다. 미래 엔티티 정의에서 기존 스키마를 재생성하지 않는다.

`DatabaseMigration.test.ts`에서 신규 생성, 행·수량·시퀀스·트리거 보존, 재실행, 실패 롤백과 백업 복구, 지원하지 않는 스키마 거절을 검증한다. 새 변경도 기존 DB 복사본과 패키징 앱에서 검증한다. 실제 사용자 DB를 테스트에 사용하지 않는다.

2026-10-07 검증: 17개 테이블, 4,359개 행을 가진 개발 DB 복사본의 모든 행이 업그레이드 전후 동일했다. arm64 패키지 앱에서도 신규 DB 생성, 기존 DB 업그레이드, preload 및 로그인 화면 로딩을 확인했다. 원본 DB 해시는 불변이다.
