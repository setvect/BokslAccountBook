# 리팩토링 작업 계획

작성일: 2026-10-07

목표는 거래·잔고 계산의 정확성을 유지하면서 IPC 실패 처리, 데이터 접근, 화면 상태 관리를 개선하는 것이다. 코드 검토에 기반한 계획이며, 2026-10-07에 아래 구현 및 완료 검증을 마쳤다.

## 사용 방법과 완료 기준

- `[ ]`는 미완료, `[x]`는 구현과 검증이 끝난 항목이다.
- 각 단계의 구현 항목과 완료 검증을 모두 충족하면 진행 현황의 해당 단계에 체크한다.
- 작업 중 발견한 기존 버그는 재현 조건을 기록하고, 동작 보존을 위한 리팩토링과 구분하여 수정한다.
- 한 번에 기능 하나 또는 책임 하나를 변경한다. 기존 `Entity → Repository → Service → IPC → UI` 구조를 유지한다.
- 금액 계산 결과나 DB 스키마가 달라지는 작업은 기존 데이터와의 호환성을 별도로 검증한다.
- 단계별 완료 기록에는 변경 파일, 실행한 검증 명령과 결과, 남은 문제를 적는다.

- [x] 서비스에 테스트용 DataSource 또는 Repository를 전달할 수 있도록 필요한 범위부터 의존성 주입 지점을 만든다.
- [x] 샘플 데이터 생성을 일반 `npm test` 대상에서 분리하고, 명시적으로 실행하는 개발 도구로 옮긴다.
- [x] 순수 함수·서비스 테스트가 Electron 실행이나 main/renderer 번들 생성 없이 실행되도록 Jest 환경과 사전 검사를 분리한다.
- [x] `tsc --noEmit` 기반 타입 검사 명령을 추가하고, 기존 오류를 기록한 뒤 검사 통과 상태를 만든다.
- [x] 리팩토링 전 기준 테스트를 작성한다: 수입·지출·이체의 수수료 반영, 등록 후 삭제 시 잔고 복원, 수정 시 기존 변화 취소, 저장 실패 시 롤백.
- [x] **완료 검증:** 일반 테스트를 연속 두 번 실행해 통과하며, 개발 DB의 스키마와 데이터가 바뀌지 않고 타입 검사가 통과한다.

## 2. IPC 요청·응답과 오류 처리

대상: `src/common`, `src/main/IpcHandler.ts`, `src/main/preload.ts`, `src/renderer/common/IpcCaller.ts`, `src/renderer/App.tsx`

현재 요청은 UUID별 응답을 기다리지만 실패는 공통 오류 채널로만 전달된다. 이때 원래 요청의 Promise가 끝나지 않을 수 있다.

- [x] 채널별 요청·응답 타입과 공통 오류 형식을 정의한다. 요청 응답과 일방향 알림 이벤트를 구분한다.
- [x] preload 경유 구조를 유지하면서 공통 호출 방식을 정한다. `invoke/handle` 전환 또는 기존 응답 방식 보완 중 하나를 선택하고 이유를 기록한다.
- [x] 공통 호출부에서 성공·실패·시간 초과를 처리하고, 직접 등록한 응답 리스너와 타이머를 정리한다. 시간 초과가 main 작업 취소를 뜻하지 않음을 반영해 저장 요청을 자동 재시도하지 않는다.
- [x] 분류 기능의 조회·등록·수정·정렬·삭제에 먼저 적용하고, 기존 호출부와 함께 동작하는지 확인한다.
- [x] 검증된 방식을 계좌·코드·즐겨찾기·거래·매매·환전·메모·스냅샷·통계·사용자·설정 기능으로 순차 확대한다.
- [x] 요청 실패가 호출자에게 전달되도록 하고, 화면 오류 안내가 공통 처리와 중복되지 않도록 정리한다.
- [x] main 진입점에서 요청값의 형태와 필수 필드를 검증하고, 업무 규칙 검증은 서비스에서 수행하도록 책임을 정한다.
- [x] **완료 검증:** 성공, 서비스 예외, 응답 없음, 동시 요청을 검증한다. 모든 요청이 성공 또는 실패로 종료되고 직접 등록한 리스너가 남지 않는다.

## 3. 잔고 계산과 트랜잭션 정리

대상: `TransactionService`, `ExchangeService`, `TradeService`, `AccountService`, `StockBuyService`, 관련 Repository

현재 거래 등록·삭제에 잔고 변화의 정방향·역방향 계산이 중복되어 있다. 계좌 저장과 잔고 재생성은 하나의 트랜잭션으로 묶여 있지 않다.

- [x] 수입·지출·이체·환전·매매의 잔고 및 보유수량 변화 규칙을 표로 기록한다. 수수료 통화와 반올림 시점도 명시한다.
- [x] 일반 거래부터 입력값을 받아 계좌·통화별 변화량을 반환하는 순수 함수를 추출한다.
- [x] 등록은 변화량 적용, 삭제는 반대 변화량 적용, 수정은 이전 변화 취소 후 새 변화 적용으로 통일한다.
- [x] 환전·매매에도 같은 원칙을 적용하되, 매매 손익·보유수량 등 서로 다른 업무 규칙은 명시적으로 유지한다.
- [x] 계좌 저장·수정과 잔고 저장·삭제를 하나의 트랜잭션으로 묶는다.
- [x] 트랜잭션 내부의 조회와 저장이 동일한 EntityManager를 사용하도록 정리한다.
- [x] DB 조회, 업무 계산, 응답 모델 변환을 분리하고, 동기 변환에 불필요한 `async`와 `Promise.all`을 제거한다.
- [x] **완료 검증:** 계좌·통화·금액 변경, 수수료, 잔고가 없는 통화, 매매 수정·취소를 임시 DB로 확인한다. 중간 저장 실패 시 거래·잔고·보유수량이 함께 복원된다.

## 6. DB 마이그레이션 도입

현재 정책: 사용자 요청에 따라 `CB_STOCK_BUY.QUANTITY`, `CC_TRADE.QUANTITY`는 INTEGER로 유지한다. 이미 적용된 REAL 변경 이력을 보존하고, 정수 여부 검사 후 복원하는 후속 마이그레이션을 추가했다. 아래 최초 완료 기록의 소수 수량 지원은 후속 수정으로 철회했다.

대상: `src/main/config/AppDataSource.ts`, `src/main/entity/Entity.ts`, DB 초기화·시작 흐름, 배포 설정

- [x] 현재 스키마와 지원할 기존 DB 상태를 조사하고, 신규 설치와 기존 사용자 DB의 초기 마이그레이션 기준을 정의한다.
- [x] 신규 빈 DB 생성과 기존 DB의 마이그레이션 이력 도입 절차를 구현한다. 기존 테이블을 중복 생성하지 않도록 확인한다.
- [x] DB 백업, 마이그레이션 실행, 실패 시 시작 중단과 복구 안내 순서를 정한다. DB 연결 실패가 후속 초기화로 진행되지 않도록 오류를 전달한다.
- [x] 신규 DB와 기존 DB 복사본에서 업그레이드를 검증한 뒤 운영 환경의 `synchronize`를 끈다.
- [x] 초기 데이터·샘플 데이터와 엔티티의 호환성을 확인하고, 마이그레이션 코드가 패키징 결과에 포함되는지 확인한다.
- [x] **완료 검증:** 신규 설치, 기존 DB 업그레이드, 재실행 시 중복 적용 방지, 실패 후 백업 복구를 검증한다. 사용자 데이터와 잔고·통계 결과가 보존된다.
